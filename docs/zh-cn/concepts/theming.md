# 主题系统

> **原理讲解** —— 介绍 VexGo 如何把一个主题目录变成服务端渲染的页面：请求管线、模板解析规则、语言选择、缓存机制，以及主题自带的种子页面会经历什么。读这一页是为了理解主题系统**为什么**这样设计。具体操作请看[主题开发指南](/zh-cn/guides/theme-development)，精确的字段与函数表请看[主题模板参考](/zh-cn/reference/theme-templates)。

## 概览

VexGo 的公开页面由服务端渲染。访客打开 `/`、`/post/my-post`、`/about` 或 `/user/2` 时，后端执行当前主题里的一个 Go 模板，直接返回渲染好的 HTML。访客的浏览器不需要执行 JavaScript 就能读到内容，搜索引擎拿到的是完整标记，所有客户端收到的 HTML 完全一致。

管理面板是另一块非公开区域：它位于 `/admin/` 下，是一个 JavaScript 单页应用。除 API 路由和静态资源路由之外，其余请求要么是 SSR 公开页面，要么是 404。

一个**主题**就是一个目录，里面是 HTML 模板、可选的 `i18n/` 字典目录、可选的 `seed/` 默认页面目录，以及存放 CSS、JavaScript 和图片的 `assets/` 目录。没有编译步骤，也没有插件接口：主题只是渲染器读取的数据。

## 主题存放位置

有两类主题，渲染器对它们一视同仁：

- **默认主题**被编译进后端二进制文件，始终可用、无法删除，并且在当前主题无法解析时作为兜底。
- **上传主题**从 ZIP 包解压到 `data/theme/<id>/`，上传后立即可用。

**当前主题**是数据库里的一个值。切换它会在下一次请求生效，无需重启；每个请求只解析一次主题，所以同一个页面不会混用两个主题。

## 一次请求的历程

路由注册了一小组公开路由，其余请求由兜底处理器接管。每条路由先解析主题、再组装模板数据、最后渲染一个模板：

| 请求                                                | 模板文件                                 | 模板上下文     |
| --------------------------------------------------- | ---------------------------------------- | -------------- |
| `/`（支持 `?search=`、`?category=`、`?page=` 过滤） | `index.html`                             | `IndexData`    |
| `/post/<slug>`、`/posts/<slug>`                     | `post.html`                              | `PostData`     |
| `/<slug>`                                           | `<slug>.html` → `page.html` → `404.html` | `PageData`     |
| `/user/<id>`                                        | `user.html`                              | `UserData`     |
| 未匹配的路径                                        | `404.html`（可选）                       | `NotFoundData` |

这张表里有两个刻意的设计：

- **自定义页面的模板链是逐级回退，而不是直接失败。** 访问 `/<slug>` 时，如果主题提供了专用的 `<slug>.html` 就用它，否则用通用的 `page.html`，再否则用 404 模板并返回 404 状态码。这正是默认主题能给自己的 `links` 和 `timeline` 种子页配专属布局，同时让其他所有 slug 走 `page.html` 的原因。
- **内容可见性在模板执行之前就已确定。** 草稿和待审文章在查询阶段就被过滤掉了，所以猜测 slug 只会渲染 404 页面，不会泄露未发布内容。唯一的例外是管理员的草稿预览，指南里有说明。

如果某个路由的模板缺失，或在渲染时解析失败，响应会降级为纯文本 `404`，而不是抛出堆栈信息——线上站点用了坏主题的结果是「页面不存在」，而不是「服务器错误」。

## 模板如何解析

主题根目录下的所有 `.html` 文件会被解析进**同一个**模板集合。这让 Go 的 `{{define "name"}}` / `{{template "name"}}` 机制可以跨文件工作：主题可以把页头和页脚放在 `partials.html`（文件名随意）里，然后在每个页面中引入。

有五个文件名对服务端有特殊含义，其余都是可选的：

- `index.html`、`post.html`、`page.html`、`user.html` —— 四个页面模板
- `404.html` —— 未找到页面模板
- 其他任意根目录下的 `<slug>.html` —— 该 slug 对应自定义页面的专用模板。含斜杠、以点开头或含大写字母的文件名会被忽略，只有纯小写的 `<slug>.html` 才算数。

主题至少需要提供上述五个名称中的一个，才算有效；并且**激活主题时会校验它提供的每个模板都能解析通过**。语法错误的主题会在激活阶段被拒绝，而不是等到线上页面崩掉才发现。由于每个页面模板都必须是完整的 HTML 文档，通常以 `<!DOCTYPE html>` 开头。

## 静态资源来自哪里

模板里从不出现主题名，资源一律通过固定前缀引用：

```html
<link rel="stylesheet" href="/theme-assets/style.css" />
```

服务端把 `/theme-assets/<file>` 解析到**当前**主题的 `assets/` 目录。注意 `assets/` 这一段是服务端补上的：磁盘上的文件是 `assets/style.css`，但 URL 是 `/theme-assets/style.css`。这样模板可以在主题之间原样拷贝，两个主题也可以各自拥有同名的 `style.css` 而不冲突。

由于资源和公开站点同源，主题里的 JavaScript 以站点的权限运行。这就是上传主题必须是管理员操作的原因——参见[信任边界](#信任边界)。

## 语言如何确定

语言处理刻意分成服务端和主题两部分：

1. 服务端为每个请求解析出一个**访客语言**，优先级为：
   `?lang=` 查询参数 → `vexgo_lang` cookie → `Accept-Language` 请求头 → 站点配置的默认语言 → `en`。
   合法的 `?lang=` 值会写进 cookie 保留一年，所以切换语言后翻页仍然保持。
2. 主题用 `i18n/<lang>.json` 提供扁平的键值字典。
3. 服务端按回退链 **`en` → 站点默认语言 → 访客语言** 逐键合并字典，所以翻译不全的主题只会逐键回退，不会整页失败。所有字典都没有的键会原样渲染成键名本身，这让缺失的翻译在页面上直接可见，而不是悄无声息。

合并顺序有一个值得注意的后果：站点默认语言会**覆盖**主题的 `en` 字符串，访客语言又覆盖两者。因此一个提供 `en.json` 和 `zh.json` 的主题，在配置为中文的站点上，只有当 `en.json` 存在且访客语言解析为 `en` 时才会给英语访客渲染英文——而这是成立的，因为 `en` 是回退链的最后一环。

解析结果通过 `.Site.Language` 暴露给模板，`t` 辅助函数从合并后的字典中取值：

```html
<h1>{{t "nav.home"}}</h1>
```

后端不硬编码任何自己的字符串。主题在 `i18n/` 下提供什么，就能提供什么——这也是没有 `i18n/` 目录的主题照样能用的原因：所有 `{{t "..."}}` 都渲染成键名。

## 缓存与热更新

解析后的模板按主题缓存，缓存键是该主题文件的最新修改时间，因此只有主题发生变化时才会重新从磁盘读取。这带来两个实际影响：

- 上传、覆盖或删除主题会自动使其缓存失效；改过的模板在下次请求就会生效，无需重启服务。
- 切换当前主题是一次数据库写入，而不是一次部署。

对主题作者来说，这意味着迭代不需要重新构建：改模板、重新上传（或直接覆盖文件）、刷新页面即可。

## 种子页面

主题可以在 `seed/` 下提供 Markdown 文件，用来引导创建自己的自定义页面：

```text
seed/about.md
seed/links.md
```

每个文件命名为 `<slug>.md`，可带 YAML frontmatter，slug 必须符合页面 slug 规则（小写 ASCII 字母、数字和连字符）。主题被激活时，服务端会为每个「slug 尚不存在」的种子文件创建一个页面，每次启动时也会执行同样的检查。

关键在于**尚不存在**：种子只是起点，永远不是重置。在管理面板里编辑或删除一个种子页面是安全的——下次激活不会重新创建或覆盖它。种子页面的作者是站点的第一个超级管理员（没有则取第一个管理员），所以全新安装且尚无管理员时，服务端只会跳过种子创建。

默认主题首次运行时出现在导航里的 **Links** 和 **Timeline** 页面，就是这么来的。

## 信任边界

公开 SSR 页面与管理面板同源，因此主题系统的信任模型值得明说：

- 主题的模板和 `assets/` 里的 JavaScript 在公开站点的源（origin）下运行。因此恶意主题等价于在公开站点上注入脚本——如果管理员浏览了套用该主题的站点，它甚至能读取管理面板的 `localStorage`。上传主题之所以限定为管理员操作，正是这个原因。
- 主题模板不能执行 Go 代码、注册路由或查询数据库。它们只能拿到[主题模板参考](/zh-cn/reference/theme-templates)里描述的数据上下文。
- Markdown 内容以 GFM 扩展和安全默认值渲染：Markdown 中的原始 HTML 会被转义而不是直通。渲染结果是 `ContentHTML`，也是主题唯一可以不转义输出的值。
- 模板输出的其他内容都会由 Go 的 `html/template` 自动转义，所以标题里带 `<script>` 的文章只会显示成文本，不会被执行。
